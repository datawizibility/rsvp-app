Product & Developer Guide

RSVP App

One platform to invite, manage and host an event — a universal Event + Contact + Guest + Invitation + RSVP engine, demonstrated through a wedding.

🎯 Build #1 — the core loop 🧱 Next.js · Prisma · Postgres ✅ 22 unit + 2 e2e tests
This guide has two audiences Product owners can read What is RSVP App through Demo tour. Developers can jump to Data model, Architecture, Local setup and Testing.

What is RSVP App

Most invitation tools stop at a pretty page. RSVP App starts there and keeps going — it owns the whole guest journey: build the invitation, import the guest list, send personal links, collect RSVPs, and watch it all on a live dashboard.

It is deliberately built as an engine, not a wedding app. A wedding is the first experience; investor meets, conferences, birthdays and corporate events are configuration, not new products.

The positioning

Create. Invite. RSVP. Manage.

The moat is not templates Templates and pretty designs get copied. The durable value is the guest data + event history + workflow + communication. Own the guest, and switching cost grows with every event.

Who it's for

🧑‍🤝‍🧑 Individual organiser

A family hosting a wedding. Needs to create an invitation, upload a guest list, send it out, track who's coming, and manage several functions (Mehendi, Sangeet, Wedding, Reception).

🏢 Corporate organiser

A company running an investor meet. Needs a branded event page, an agenda, VIP tracking, custom questions ("Would you like a meeting with management?"), and analytics.

Both run on the same engine There is no WeddingGuest vs InvestorGuest table. One Contact + one EventGuest serves every vertical. A test proves the investor case works with zero schema change.

Feature tour

Accounts & workspaces

  • Email + password sign-up; a personal workspace is created automatically.
  • The workspace is the tenancy boundary — it's what lets a wedding user later become a corporate or agency user without a new account.

Events & functions

  • Create an event with type, dates, city, venue, host and contact.
  • Add unlimited functions — each with date, times, venue, dress code, capacity and whether RSVP is required.
  • Event lifecycle status: draft published completed archived.

Invitation builder

  • Two templates — Royal (ornate, gold, serif) and Minimal (clean, image-forward).
  • Editable content: headline, welcome, about, host message, venue note, RSVP message.
  • Toggle 13 sections on/off: welcome, about, functions, gallery, venue, directions, dress code, accommodation, travel, RSVP, contact, gift registry, agenda.
  • Upload a cover image and a gallery.
  • Live preview while you edit; one-click Publish (increments a version and flips the event to published).

Guest management

  • Add guests manually, or import via a guided CSV wizard.
  • Custom per-event groups (Bride Family, Friends, VIP, Investors, Media…).
  • VIP flag and party size per guest, per event.
  • Each guest gets a unique, non-enumerable personal link.

CSV import wizard

Upload → detect columns → map → validate → detect duplicates → preview → import. It recognises messy headers (e.g. Mob No → mobile, Company → organisation) and reports "487 records: 451 ready, 28 need review, 8 duplicates".

Personalised invitation & RSVP

  • Guests open /e/<event>/<token> and see their own name, VIP badge and function list.
  • RSVP: Yes / Maybe / No, adult + child counts, per-function attendance, dietary preference, accommodation & travel needs, and custom questions.
  • Re-submitting updates the response (latest wins).

Dashboard & metrics

  • Invited · Opened · Responded · Confirmed · Maybe · Declined · Pending.
  • VIP confirmed / VIP total, and attendance by function.
  • Workspace summary: events, contacts, confirmed guests.
Share without an API In this build, sending is a personal link you copy or a wa.me WhatsApp deep link. Automated WhatsApp Business messaging is a later subsystem.

Core concepts

Contact vs EventGuest the key idea

There are two different things people confuse:

Contact workspace-level

Who the person is. One record per person for the whole workspace — name, mobile, email, organisation, designation, city. Deduplicated by normalised mobile number.

EventGuest event-level

Their participation in one event — group, VIP flag, party size, and the personal invitation token. A person has one EventGuest per event they attend.

So Raj Mehta of ABC Capital is one Contact, and a separate EventGuest at Investor Meet 2026, the AGM, and next year's meet. That's what turns a guest list into a CRM over time.

The invitation token lives on EventGuest, not Contact The same person can be a VIP at one event and an ordinary guest at another, with a different party size. The token must be per-event.

Personalised links

The invitation page is shared; the guest-specific parts are overlaid at render time.

https://your-app.vercel.app/e/rahul-neha-wedding/7H82KQ9M2PX4T8VW3N6BZ1LD5R

Tokens are 26-character base32 (~130 bits) so they can't be guessed or enumerated.

Verticals are configuration

Wedding dietary preference, investor meeting requests, conference sessions — all live in generic EventQuestion / RsvpAnswer rows and JSON custom fields. Adding a vertical means adding questions, not tables.

Data model

Thirteen tables. The relationships are deliberately simple: everything hangs off a Workspace, and guests hang off Events.

MutationsServer Actions — thin: validate (zod) → call service → revalidate

MediaLocal disk in dev, Vercel Blob in production
TestsVitest (unit/integration) + Playwright (e2e)

Two rules that keep it sane

  1. All business logic lives in lib/services/*. Server actions and pages are thin wrappers. This is why the CSV engine, metrics and token logic are unit-testable without a database.
  2. Ownership is enforced in services, not the UI. Every organiser operation re-checks that the event's workspace belongs to the signed-in user.

cp .env.example .env
#   DATABASE_URL      local Postgres
#   TEST_DATABASE_URL used by integration tests
#   AUTH_SECRET       npx auth secret

# 3. create databases + migrate
createdb rsvp_app_dev
createdb rsvp_app_test
npx prisma migrate dev

# 4. seed the demo wedding
npm run db:seed

# 5. run
npm run dev   # http://localhost:3000

FAQ & troubleshooting

Why one Guest table instead of per-vertical tables?

Because a person is the same person across events. One Contact + one EventGuest avoids duplicate records and gives you a CRM for free. Vertical differences are data (custom questions, JSON fields), not schema.

What happens if two people share a mobile number?

They collapse into one Contact (dedup is by normalised mobile). Acceptable for the MVP; merge/split tooling is deferred. Use distinct numbers for distinct people.

Can a guest RSVP more than once?

Yes — Rsvp is 1:1 with the guest, so a second submission overwrites the first ("latest wins"). Attendance and custom answers are replaced transactionally.

Are invitation links secure?

Tokens are ~130-bit random base32, so they can't be enumerated. Anyone with the link can view and RSVP — that's the intent of an invitation. RSVP submissions are rate-limited.

Why don't uploads work after deploying?

Vercel's filesystem is ephemeral. Ensure BLOB_READ_WRITE_TOKEN is set for Production and redeploy. In dev, files go to public/uploads.

Can I add a new event type (conference, AGM)?

Yes — EventType already includes them. You'd typically add custom questions and maybe a new template. No schema change required.

How do I send invitations at scale?

Not in this build. Sending is manual (copy link / WhatsApp deep link). Automated WhatsApp Business messaging and reminders are the next subsystem.
